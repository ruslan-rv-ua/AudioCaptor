# AudioCaptor — посібник розробника

AudioCaptor — портативний записувач звуку для Windows: Tauri v2, бекенд на Rust, інтерфейс на Svelte 5 і
TypeScript у WebView2. Тут описано, що встановити, як зібрати й перевірити програму, як ведеться робота і як
випустити нову версію.

Найважливіша вимога — доступність для користувачів екранних читачів: кожна зміна інтерфейсу зберігає доступ
із клавіатури, підписи й озвучення змін стану (розділ «Доступність»).

## Технології

| Шар | Технологія |
|-----|------------|
| Фреймворк | [Tauri v2](https://v2.tauri.app/) (бекенд на Rust + інтерфейс у WebView) |
| Бекенд | Rust (редакція 2021) |
| Інтерфейс | Svelte 5 + TypeScript + Vite |
| Переклади інтерфейсу | Paraglide JS (inlang), тексти в `messages/` |
| Захоплення звуку | [wasapi](https://github.com/HEnquist/wasapi-rs) (обгортка WASAPI) |
| Мікшування | Мікшер реального часу зі зміною частоти дискретизації через [rubato](https://github.com/HEnquist/rubato) |
| Запис WAV | Власний код (`audio/writer.rs`): WAV, а понад 4 ГБ — RF64. [hound](https://github.com/ruuda/hound) лишився тільки в тестах |
| Стиснення Opus | [libopus](https://opus-codec.org/) через крейти [opus](https://github.com/SpaceManiac/opus-rs) і `opusic-sys` (код на C, збирається CMake); контейнер Ogg — [ogg](https://github.com/RustAudio/ogg) (рішення decision-8) |
| Стиснення MP3 | Кодер, вбудований у Windows: [MP3 Audio Encoder](https://learn.microsoft.com/en-us/windows/win32/medfound/mp3-audio-encoder) з Media Foundation, через крейт `windows`; сторонньої бібліотеки MP3 немає (рішення decision-5) |
| Стиснення FLAC | [libFLAC](https://xiph.org/flac/) 1.5.0 через крейт [libflac-sys](https://github.com/mgeier/libflac-sys) без Ogg (код на C, збирається CMake); кодер і декодер викликаються напряму (рішення decision-10) |
| Звукові сигнали | [rodio](https://github.com/RustAudio/rodio) (OGG, вбудовані через `include_bytes!`) |
| Глобальна гаряча клавіша | `tauri-plugin-global-shortcut` |
| Одна копія програми | `tauri-plugin-single-instance` |
| Вибір теки | `tauri-plugin-dialog` |
| Журнал | `tauri-plugin-log`: файл у `AudioCaptor-data/logs/` і консоль `just dev` (розділ «Портативний режим») |
| Менеджер пакетів | [pnpm](https://pnpm.io/) |
| Запуск команд | [just](https://github.com/casey/just) |

## Що потрібно встановити

- **Windows 10 або новіша** — програма працює лише у Windows.
- **Rust** через [rustup](https://rustup.rs/). Версію й компоненти задає `rust-toolchain.toml`: rustup ставить
  їх сам під час першої команди `cargo` у теці проєкту. Поставити наперед можна командою
  `rustup toolchain install` у корені проєкту — так робить CI.
- **Microsoft C++ Build Tools** з набором «Desktop development with C++»
  ([завантаження](https://visualstudio.microsoft.com/visual-cpp-build-tools/)): ними Rust для Windows
  компонує exe.
- **[CMake](https://cmake.org/download/)** — ним під час `cargo build` збираються дві бібліотеки, написані
  на C: libopus, кодер Opus (його приносить крейт `opusic-sys`), і libFLAC (крейт `libflac-sys`). Команда
  `cmake` має бути в PATH: поставте CMake через `scoop install cmake` або інсталятором із сайту. Перевірено
  з CMake 4.5; на образі `windows-latest`, де працюють CI і Release, він уже є. Без CMake збирання
  зупиняється на крейті `opusic-sys` або `libflac-sys`. Налаштування цих бібліотек — у розділі «Бібліотеки
  на C: файл CMake».
- **[Node.js](https://nodejs.org/) 22** — цю версію ставлять CI і Release. Мажорна версія `@types/node` у
  `package.json` така сама, тож перехід на інший Node міняє і `node-version` у `ci.yml` та `release.yml`, і
  `@types/node`. Vite 8 і `@sveltejs/vite-plugin-svelte` 7 працюють з Node 20.19+, 22.12+ або 24+; Node 18 уже
  не підходить.
- **[pnpm](https://pnpm.io/) 10**: `npm install -g pnpm@10`. Точну версію записано в `package.json`
  (`"packageManager": "pnpm@10.32.1"`), і CI бере її звідти. Без `@10` npm поставив би новішу основну версію
  pnpm, ніж у CI.
- **[just](https://github.com/casey/just)** — запускає `just check`, `just smoke` і решту рецептів із
  `justfile`. Рецепти just виконує через `sh`, тож `sh` має бути в PATH (наприклад, з Git for Windows;
  Scoop-пакет `git` додає його сам). Без нього just пише «could not find the shell `sh`».
- **[WebView2 Runtime](https://developer.microsoft.com/en-us/microsoft-edge/webview2/)** — уже є в Windows 11
  і на більшості комп'ютерів з Windows 10.
- Для роботи з проєктом: [git-flow-next](https://github.com/gittower/git-flow-next) (команда `git flow`),
  [Backlog.md](https://github.com/MrLesk/Backlog.md) (команда `backlog`) і
  [GitHub CLI](https://cli.github.com/) (команда `gh`: запуск workflow і перегляд релізів).
- Для `just smoke`: NVDA і Windows PowerShell 5.1 (є у Windows).

## Початок роботи

```powershell
pnpm install
just dev
```

`just dev` (те саме, що `pnpm tauri dev`) збирає програму й відкриває її вікно. Зміни в Rust перезбирають
програму, зміни інтерфейсу з'являються одразу. Файли перекладів у `src/paraglide/` Vite генерує сам; у git їх
немає.

У цьому режимі exe називається `src-tauri/target/debug/audio-captor.exe` (назву `AudioCaptor.exe` дають лише
`just build` і `just build-fast`), а свої дані копія тримає в `src-tauri/target/debug/AudioCaptor-data/`, дані
вбудованого браузера — у `src-tauri/target/debug/AudioCaptor-webview/`.

Перед `just dev` закрийте свій AudioCaptor, якщо він запущений. Програма дозволяє лише одну копію, тож копія
для розробки тільки покаже вікно вже запущеної і закриється.

## Як ведеться проєкт

Проєкт веде один власник. Правила для агентів Claude Code записано в `CLAUDE.md`; нижче головне з них. Власник
координує роботу в головній сесії Claude Code, а кожну задачу віддає окремій робочій сесії на власній гілці.

### Задачі, рішення й дослідження: Backlog.md

Усе, що треба зробити, що вирішено й що досліджено, лежить у теці `backlog/`. Її веде
[Backlog.md](https://github.com/MrLesk/Backlog.md) — програма командного рядка `backlog`. Записи в ній
пишуться українською.

| Що | Команда |
|----|---------|
| Задачі | `backlog task list --plain`; одна задача — `backlog task 8 --plain` |
| Чернетки: робота, що чекає рішення власника чи даних ззовні | `backlog draft list --plain` |
| Рішення | `backlog decision list --plain`; одне рішення — `backlog decision view decision-1 --plain` |
| Дослідження та інші документи | `backlog doc list --plain`; один документ — `backlog doc view doc-3 --plain` |
| Етапи | `backlog milestone list --plain` |
| Пошук усюди | `backlog search "NVDA" --plain` |

- Файли в `backlog/` змінюють лише командами `backlog` (виняток — `backlog/config.yml`): так зберігаються
  зв'язки між записами та їхня історія. Довідка — `backlog <команда> --help`.
- `backlog` запускають з PowerShell, не з Git Bash: Git Bash перетворює аргументи на кшталт `/api` на шляхи
  Windows.
- Роботу, знайдену мимохідь, спершу записують у backlog як задачу чи чернетку; до неї беруться лише зі слова
  власника.
- Кожна задача й чернетка має по одній мітці `model-*` і `effort-*`: рекомендовану модель Claude і рівень
  зусиль.
- Кожна задача має список Definition of Done (типовий записано в `backlog/config.yml`): `just check`, тексти
  інтерфейсу двома мовами, перевірка з клавіатури й NVDA, документація, `CHANGELOG.md`.
- Виконана задача переходить у стан Done, а потім в архів (`backlog/archive/`). Її однаково можна прочитати
  командою `backlog task <номер> --plain`.

### Гілки: git flow

Репозиторій працює за git flow з інструментом [git-flow-next](https://github.com/gittower/git-flow-next).
Налаштування показує `git-flow overview`, довідку — `git-flow <команда> --help` (`git flow --help` не
працює).

- Кожну задачу роблять на окремій гілці від `develop`, названій за задачею:
  `git flow feature start task-12-flac-export`; для виправлення помилки — `git flow bugfix start <назва>`.
- Коли гілку завершувати, вирішує власник: `git flow feature finish <назва> --no-fetch --no-push` (для
  помилки — `git flow bugfix finish <назва> --no-fetch --no-push`).
- Зміни лише в `backlog/` і `CLAUDE.md` комітять прямо в `develop`, без гілки.
- `main` змінюється тільки під час випуску (розділ «Порядок випуску»).
- Гілки завершують локально; pull request відкривають, лише коли власник про це просить. Push і запуск
  workflow на GitHub — тільки з дозволу власника.
- Налаштування git flow зберігаються лише в `.git/config` цієї копії репозиторію: спільного файлу з ними
  немає.

### Перевірки: `just check`

`just check` запускає всі локальні перевірки по черзі й зупиняється на першій помилці:

1. `pnpm vite:build` — збирає інтерфейс і генерує `src/paraglide/` (без цих файлів `pnpm check` не працює);
2. `pnpm check` — svelte-check і перевірка типів TypeScript;
3. `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings`;
4. `cargo test --manifest-path src-tauri/Cargo.toml`;
5. `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check`.

Push на GitHub не запускає CI, тож саме локальний `just check` вирішує, чи задача готова. CI повторює ті самі
перевірки лише для pull request і на запит (розділ «CI»).

Rust-код форматується стандартним стилем rustfmt. Перед комітом:

```powershell
cargo fmt --manifest-path src-tauri/Cargo.toml
```

Версію Rust закріплено у файлі `rust-toolchain.toml` (зараз 1.99.1 з компонентами clippy і rustfmt). Так новий
випуск Rust із новими правилами clippy не зробить перевірки червоними сам собою. Зміна цієї версії — окрема
свідома задача. CI і Release ставлять ту саму версію з цього файлу.

### Мови й тексти

- Код, коментарі в коді й повідомлення комітів — англійською. Записи в Backlog і цей документ — українською.
- Кожен новий чи змінений текст інтерфейсу має бути англійською й українською: у `messages/en.json` і
  `messages/uk.json`. Підписи меню трея перекладаються в Rust, у `src-tauri/src/tray.rs` (рішення
  decision-4).
- `CHANGELOG.md` пишуть для користувачів: лише зміни, які вони помітять (нові можливості, виправлення, змінена
  поведінка). Інструменти, тести, CI й збирання туди не потрапляють. Нові записи йдуть у розділ
  `## [Unreleased]`.
- Кожен пункт `CHANGELOG.md` — один рядок, без ручних переносів, хоч би яким довгим він був. Release бере розділ
  версії як є описом релізу на GitHub, а там кожен перенос рядка стає новим рядком: речення рвуться, і NVDA в
  режимі огляду читає пункт уривками (TASK-24).
- Paraglide завантажує два модулі inlang з jsDelivr за адресами в `project.inlang/settings.json` і виконує їх під
  час кожної збірки інтерфейсу: `@inlang/plugin-message-format` (читає `messages/*.json`) і
  `@inlang/message-lint-rule-missing-translation`. Версії в адресах закріплені (TASK-40), тож нова публікація
  пакета сама до збірки не потрапить. Щоб оновити модуль:
  1. Подивіться версії: `npm view @inlang/plugin-message-format versions dist-tags` (так само для другого
     пакета). Мажорна версія має підходити до встановленого `@inlang/paraglide-js`; про несумісність з
     Paraglide 2 пише список змін пакета.
  2. Змініть номер версії в адресі в `project.inlang/settings.json`.
  3. Запустіть `pnpm vite:build` до й після зміни, скопіювавши `src/paraglide/` перед зміною, і порівняйте
     обидві копії (`git diff --no-index <копія> src/paraglide`): тексти обома мовами не мають змінитися.
  4. Запустіть `just check` і `just build`.

| Профіль | Оптимізації | Для чого |

| `release` | `lto=true`, `codegen-units=1`, `opt-level="s"`, `strip=true`, `panic="abort"` | Випуск |
| `release-fast` | `lto=false`, `codegen-units=16`, `opt-level=1`, `strip=false`, `panic="unwind"` | Швидкі збирання під час розробки |

Зібраний exe лежить тут:

- **release**: `src-tauri/target/release/AudioCaptor.exe`
- **release-fast**: `src-tauri/target/release-fast/AudioCaptor.exe`

Назву `AudioCaptor.exe` задано явно (`mainBinaryName` у `src-tauri/tauri.conf.json`); на неї спираються
Release і маніфест Scoop (рішення decision-2).

### Бібліотеки на C: файл CMake

libopus і libFLAC написано на C; під час `cargo build` їх збирає CMake через крейт `cmake`. Файл
`src-tauri/cmake/msvc-toolchain.cmake` задає для них дві речі (рішення decision-10):

- **Статичний C runtime**, як `+crt-static` для Rust у `.cargo/config.toml`. libFLAC вимагає
  політик CMake до 3.31, тому бере runtime зі змінної `CMAKE_MSVC_RUNTIME_LIBRARY`, а не з прапорця `-MT`,
  який передає крейт `cmake`. Без файлу вона збирається з динамічним runtime, і exe не компонується
  (помилка LNK1120). libopus вмикає статичний runtime сама (`OPUS_STATIC_RUNTIME` у `opusic-sys`).
- **Оптимізацію.** Для генератора Visual Studio крейт `cmake` замінює `CMAKE_C_FLAGS_<CONFIG>` прапорцями
  без `/O`. Без файлу libFLAC додає до exe близько 700 КБ замість 140 і кодує втричі повільніше (TASK-11).
  Файл повертає типові прапорці CMake: `/O1` для MinSizeRel (профіль `release`, `opt-level = "s"`), `/O2`
  для Release (профіль `release-fast`) і RelWithDebInfo (профіль `dev`, див. нижче). libopus збирається
  через Ninja, якщо він є в PATH (на `windows-latest` є), і тоді прапорці в неї й так на місці; без Ninja
  файл повертає їх і їй.

Файл підключає змінна `CMAKE_TOOLCHAIN_FILE_x86_64_pc_windows_msvc` у розділі `[env]` файлу
`.cargo/config.toml` у **корені репозиторію**. Там же лежить `+crt-static`. Cargo шукає цей файл у теці, де
його запущено, і в її батьківських теках, а не біля `Cargo.toml`. Тому файл лежить у корені: його бачать
усі виклики cargo — і з кореня з `--manifest-path` (`just check`, кроки CI і Release), і з теки `src-tauri`
(Tauri: `just dev`, `just build`, `pnpm tauri build`). Тож clippy, тести й випуск збираються з тими самими
налаштуваннями (TASK-37). Шлях до файлу CMake у `[env]` відносний (`relative = true`), тобто рахується від
теки, де лежить `.cargo`, — від кореня.

У профілі `dev` (clippy, тести, `just dev`) `src-tauri/Cargo.toml` піднімає `opt-level` до 2 для
`libflac-sys` і `opusic-sys`. Інакше крейт `cmake` зібрав би бібліотеки в конфігурації Debug: без
оптимізації і з увімкненими `assert` усередині libFLAC. Так тести FLAC перевіряють libFLAC такою, як у
випуску. Решта коду в профілі `dev` лишається без оптимізації.

Якщо змінити ці налаштування, перший `just check` перезбирає всі залежності (кілька хвилин); далі він знову
швидкий.

Перевірити зібраний exe можна командою `dumpbin /dependents src-tauri\target\release\AudioCaptor.exe`: серед
бібліотек не має бути `VCRUNTIME140.dll`, а сам список має лишитися таким, як у попередньому випуску
(системні бібліотеки Windows і `api-ms-win-crt-*.dll`).

## Портативний режим

AudioCaptor — **один портативний exe**, встановлювати його не треба. Свої дані програма тримає в теці
`AudioCaptor-data/` поруч з exe (рішення decision-1), а дані вбудованого браузера — в окремій теці
`AudioCaptor-webview/` теж поруч з exe:

```
AudioCaptor.exe
AudioCaptor-data/
├── settings.json     # Налаштування й профілі
├── settings.unreadable.json  # Копія нечитабельного settings.json (з'являється лише тоді)
├── conversion-queue.json     # Записи, що чекають на конвертацію (є лише поки вони чекають)
├── logs/             # Журнали програми
└── Recordings/       # Тека записів за замовчуванням
AudioCaptor-webview/
└── EBWebView/        # Профіль WebView2: кеш і власний стан браузера
```

`settings.json` програма записує через тимчасовий файл `settings.json.tmp` із заміною (`settings::write_atomic`),
тож обрив під час збереження не лишає половини файлу. Під час запуску `settings::read_settings_at_startup`
читає файл; якщо його не вдалося прочитати (пошкоджений JSON, порожній файл, поле несподіваного типу),
програма копіює його в `settings.unreadable.json` (коли така копія вже є — в `settings.unreadable-2.json`, `-3`
тощо, стару не перезаписує) і лише потім записує типові налаштування. Звук попередження грає одразу, а
повідомлення про те, що налаштування скинуто і де лежить копія, вікно забирає командою `take_settings_notice`
і показує в блоці помилки (`role="alert"`), який читає NVDA. Якщо скопіювати не вдалося, файл лишається на місці
й під час запуску не перезаписується. Перед першим збереженням налаштувань `settings::write_settings` ще раз
пробує зробити копію (стан `WriteGuard::RetryCopy`); вдалося — зберігає як звичайно. Не вдалося знову — до
перезапуску програма `settings.json` не чіпає (`WriteGuard::Held`): збережені зміни лишаються в пам'яті, і
`read_settings` повертає їх, тож вони діють до закриття програми. Користувачеві про це окремо не кажуть (рішення
власника в TASK-46): про нечитабельний файл він уже почув під час запуску. Версії до цього виправлення стирали
такий файл мовчки.

Теки `AudioCaptor-data` програма створює під час першого запуску (`portable.rs`), а `AudioCaptor-webview` створює
Tauri, коли будує вікно.

Файл `conversion-queue.json` — це черга конвертації (розділ «Стиснені формати» нижче). Він існує, лише поки
є записи, які ще не стали стисненими файлами: програма переписує його через тимчасовий файл щоразу, коли
черга змінюється, і видаляє, коли черга спорожніла. Для кожного запису в ньому лежить шлях до WAV, кількість
кадрів, яку порахувала програма, частота, кількість каналів і формат. Шлях до WAV у теці даних записано
відносно цієї теки, тож черга переживає перенесення портативної теки на інший диск і оновлення через Scoop;
шлях поза текою даних лишається повним.

Журнал програма пише у файл `AudioCaptor-data/logs/audiocaptor.log`, а в `just dev` — ще й у консоль. Це
задано в `run()` у `src-tauri/src/lib.rs`: список місць запису замінює типовий список `tauri-plugin-log`
(`targets`, а не `target`), бо типовий пише ще й у `%LOCALAPPDATA%\com.audiocaptor.app\logs`. Рівень журналу —
Info: рядки `log::debug!` і `log::trace!` нікуди не потрапляють. Так у журнал не йдуть службові рядки бібліотеки
`wasapi` (близько сотні за секунду запису), які раніше заповнювали його. Коли файл перевищує 1 МБ, модуль
видаляє його й починає новий.

Рядок журналу має вигляд `[2026-11-27][23:17:42][audio_captor_lib][INFO] Recording started`: дата, час, модуль,
рівень, повідомлення. Час — місцевий, за годинником Windows (TASK-45). Модуль сам пише UTC, а його налаштування
`TimezoneStrategy::UseLocal` заодно ставить рівень перед модулем і в разі помилки мовчки повертається до UTC.
Тому `run()` задає власний `format`: той самий порядок полів, а час береться з `GetLocalTime`, як і для назв
файлів записів (функція `log_time`, тест `log_time_keeps_the_plugin_layout`). `chrono` для цього не потрібен.

Профіль WebView2 (кеш і власний стан браузера, без налаштувань і записів) лежить в `AudioCaptor-webview/`
(TASK-25). Це задає один параметр у `src-tauri/tauri.conf.json`:
`"appDirectoriesOverride": { "localData": "AudioCaptor-webview" }` (з Tauri 2.12). Він переносить теку локальних
даних Tauri (`app_local_data_dir`, `$APPLOCALDATA`) поруч з exe, а саме цю теку Tauri бере для профілю браузера.
Інших тек Tauri програма не використовує: свої дані вона бере з `portable::data_dir()`. Тож якщо Tauri чи плагін
покладе щось у теку локальних даних, воно опиниться в `AudioCaptor-webview`, а не в `AudioCaptor-data`. Вікно
Tauri, як і раніше, створює з `tauri.conf.json`. Без цього параметра профіль лежав би в
`%LOCALAPPDATA%\com.audiocaptor.app\EBWebView`, спільний для всіх копій програми на комп'ютері. Не підходять
`"dataDirectory"` у налаштуваннях вікна (Tauri розв'язує його всередині `%LOCALAPPDATA%`) і змінна
`WEBVIEW2_USER_DATA_FOLDER` (Tauri однаково створив би `%LOCALAPPDATA%\com.audiocaptor.app`).

Профіль лежить поза `AudioCaptor-data` (рішення власника в TASK-25): Scoop не зберігає його між оновленнями, а
резервні копії теки даних його не захоплюють. Під Scoop тека лежить у теці кожної версії, тож після оновлення
профіль починається з нуля. Якщо видалити `AudioCaptor-webview`, коли програма закрита, вона створить теку знову.

Версії до 0.1.1 включно тримали профіль браузера в `%LOCALAPPDATA%\com.audiocaptor.app\EBWebView`, а версії до
TASK-20 — ще й журнал у `logs` поруч із ним. Нинішня програма цієї теки не читає, не змінює й не видаляє: нею
може користуватися старіша копія.

## Значки

Значки генерує Tauri CLI з одного PNG:

```powershell
pnpm tauri icon src-tauri/icons/128x128.png
```

Команда перезаписує всі варіанти в `src-tauri/icons/`: ICO для Windows, ICNS для macOS, PNG різних розмірів
(зокрема логотипи Windows Store `Square*Logo.png` і `StoreLogo.png`) і значки для Android та iOS.

Вихідного файлу 1024×1024, з якого зроблено нинішні значки, у репозиторії вже немає, а `128x128.png` малий:
усе, що більше за 128 пікселів (`icon.png`, `128x128@2x.png`, ICNS, значки iOS), вийде збільшеним і
розмитим. Для нового логотипа передайте команді PNG 1024×1024.

Значок вебсторінки `public/favicon.png` (32×32) команда не створює: його роблять окремо (раніше — у
ImageMagick).

Де використовуються значки:

- `src-tauri/icons/` — усі варіанти;
- `src-tauri/tauri.conf.json` → `bundle.icon` — значки для збирання;
- `public/favicon.png` — значок вебсторінки (підключено в `index.html`);
- `README.md` і `README_UK.md` показують `src-tauri/icons/128x128.png`.

## Архітектура

### Звук: від захоплення до файлу

Звук проходить такий шлях: потоки захоплення WASAPI → кільцеві буфери → потік мікшера → запис WAV
(`WavOutputWriter`).

- **Потоки захоплення** — по одному на джерело (мікрофон, системний звук через loopback), WASAPI у спільному
  режимі.
- **Кільцеві буфери** передають звук від потоків захоплення до мікшера без блокувань.
- **Потік мікшера** за потреби змінює частоту дискретизації, застосовує гучність, обрізає піки й пише у WAV.
- **Пауза**: мікшер далі читає буфери (щоб джерела не розійшлися в часі), але нічого не пише.
- **Запис WAV** (`audio/writer.rs`) — власний код програми, без бібліотеки: 16-бітний PCM, байти рахуються в
  `u64` (TASK-50). До версії 0.4.1 включно файл писав hound, але він рахує байти в `u32` і пише лише 32-бітні
  розміри, тож понад 4 ГБ писати не може: лічильник переходив через нуль, і заголовок брехав.
- **Заголовок — 80 байтів**, розкладка та сама, що в FFmpeg з `-rf64 auto` (за EBU Tech 3306); файли
  збігаються з файлами FFmpeg байт у байт і до 4 ГБ, і після (перевірка в TASK-50). До межі файл — звичайний
  WAV: `RIFF`, chunk `fmt ` там, де й раніше (з байта 12), chunk `JUNK` із 28 нульових байтів, який
  програвачі пропускають, і початок chunk `data`. Звук починається з байта 80, а не 44, як було з hound.
- **Понад 4 ГБ — RF64** (TASK-50), розширення WAV для великих файлів. Коли розмір RIFF (довжина файлу без
  8 байтів) уже не вміщується в 32 біти — на 48 кГц це близько 6 год 12 хв, на 44,1 кГц — 6 год 45 хв (запис
  завжди стерео), — наступне оновлення заголовка переписує ті самі 80 байтів: `RIFF` стає `RF64`, з байта 12
  іде chunk `ds64` з 64-бітними розмірами RIFF і `data` та кількістю кадрів, `fmt ` переходить на місце `JUNK`
  (з байта 48), а 32-бітні поля розмірів дорівнюють 0xFFFFFFFF. Звук нікуди не зсувається, запис лишається
  одним файлом `.wav`. Заголовок пишеться одним записом, тож у файлі завжди або старий заголовок, або новий. У
  тестах межу знижено (`WavOutputWriter::with_rf64_past`). Хто відкриває RF64, перевірено в TASK-50 на файлі
  4,49 ГБ: FFmpeg і mpv, Media Foundation (через неї файли відкривають програвачі Windows) і Провідник, який
  показує тривалість. Не відкривають старий пристрій Windows MCI waveaudio і модуль `wave` з Python.
- **Заголовок WAV під час запису** (TASK-48). Після кожної секунди записаного звуку `WavOutputWriter`
  переписує заголовок із поточними розмірами (з 4 ГБ — і розмірами RF64), віддає Windows семпли з буфера й
  лишає файл відкритим. Без цього розміри з'являлися б лише під час `finalize`, а після збою програми чи
  `taskkill /F` там лишилися б нулі, і частина програвачів не показала б тривалості. Тепер після збою файл
  відкривається, а заголовку бракує щонайбільше секунди звуку. Заголовок описує лише цілі кадри. Оновлює
  заголовок потік мікшера, потоки захоплення його не чекають.
- **Буфер на дві секунди** (`BUFFER_SECONDS`, TASK-50). `BufWriter` вміщує більше звуку, ніж набирається між
  двома оновленнями заголовка, тож семпли потрапляють у файл лише разом із заголовком, що їх описує, і файл
  завжди закінчується там, де каже заголовок, також після збою. Media Foundation відкриває RF64 лише тоді,
  коли розмір RIFF у `ds64` дорівнює довжині файлу без 8 байтів. З буфером на 8 КБ файл RF64 після збою був
  на пів секунди довший за заголовок, і Media Foundation та Провідник його не відкривали, хоч FFmpeg
  відкривав. Звичайний WAV, довший за свій заголовок, Media Foundation відкриває.
- **Без примусового запису на диск.** Дані не скидаються на диск примусово (`sync_data`): усе, що програма
  віддала Windows, потрапить у файл і після її збою, а на повільній флешці примусовий запис міг би затримати
  мікшер довше, ніж вміщують кільцеві буфери (близько 200 мс). Тому після вимкнення живлення може пропасти
  більше за секунду.

### Стиснені формати: конвертація після зупинки

Запис завжди пишеться у WAV. Якщо профіль має стиснений формат, після зупинки кожен його WAV стає в чергу
й у фоні перетворюється на файл цього формату (рішення decision-7 і decision-8). У текстах для користувача це
називається «конвертація».

- **Формат профілю.** Поле `outputFormat` профілю (`settings.json` версії 6) містить ідентифікатор варіанта
  зі списку «Формат»: `Wav`, `OpusSpeech`, `OpusMusic`, `Mp3Speech`, `Mp3Standard`, `Mp3High`, `Flac`
  (`OutputFormat` у `audio/types.rs`). У профілі це
  рядок, а не перелік: формат, якого версія не знає (його записала новіша), читається без помилки, лишається
  у файлі, а запис іде у WAV (`RecordingProfile::format`).
- **Кількість кадрів.** `WavOutputWriter` рахує записані кадри, мікшер повертає їх разом зі шляхами
  (`RecordedFile`). Конвертація читає WAV і RF64 за цією кількістю (`convert/wav.rs`), а не за заголовком:
  після збою чи невдалого `finalize` заголовку може бракувати секунди, а у WAV понад 4 ГБ від версії 0.4.1
  чи старішої число в заголовку переповнене. Такий файл ще може чекати в черзі конвертації.
- **Спільний шлях** (`convert::convert_file`): кодування в тимчасовий файл `<назва>.opus.tmp`,
  `<назва>.mp3.tmp` чи `<назва>.flac.tmp`, перевірка, перейменування на `<назва>.opus`, `<назва>.mp3` чи
  `<назва>.flac`, видалення WAV. Будь-яка
  помилка до перейменування видаляє тимчасовий файл і лишає WAV. Формат додає лише свій `Codec` з двома
  методами, `encode` і `verify`; `encode_share` каже, яку частку часу займає кодування (для відсотка й оцінки
  часу).
- **Opus** (`convert/ogg_opus.rs`): libopus, application Audio, VBR без обмеження, complexity 10, кадри по
  20 мс. «Мовлення» — моно 32 кбіт/с (на 16 кГц — 24, на 8 кГц — 16), «музика» — стерео 96 кбіт/с (48 і 32).
  Частоти 8, 16 і 48 кГц кодуються як є, 44,1 кГц перетворюється на 48 кГц (`rubato`). Перевірка розкодовує
  весь файл через libopus (заодно звіряються контрольні суми сторінок Ogg) і вимагає, щоб тривалість
  збігалася з тривалістю запису до семпла.
- **MP3** (`convert/mp3.rs`): кодер MP3 Audio Encoder, вбудований у Windows (перетворювач Media Foundation,
  `CoCreateInstance` з `MP3ACMCodecWrapper`), постійний бітрейт. «Мовлення» — моно 64 кбіт/с, «стандарт» —
  стерео 128, «висока якість» — стерео 320. Кодер приймає 16-бітний PCM на частотах MPEG-1 (32, 44,1,
  48 кГц), MPEG-2 (16, 22,05, 24 кГц) і MPEG-2.5 (8, 11,025, 12 кГц), тож частота не перетворюється. Але
  бітрейти він дає лише свої (`offered_kbps`): на 44,1–48 кГц моно 48–128 кбіт/с, стерео 96–320; на 16 кГц
  моно 16–48, стерео 32–80; на 8 кГц моно 8–16, стерео 24–32. Варіант бере свій бітрейт або найбільший
  можливий (рішення decision-6). Тип виходу береться з переліку самого кодера (`GetOutputAvailableType`):
  тип із тими самими значеннями, складений вручну, кодер відкидає. Кодер пише голі кадри: без ID3, без
  заголовка Xing/Info, без CRC. У його власних типах вимкнено доповнення кадрів (прапорець
  `MPEGLAYER3_FLAG_PADDING_OFF` у структурі MPEGLAYER3WAVEFORMAT, яку тип несе в `MF_MT_USER_DATA`), і на
  44,1 кГц кадр тоді вміщає менше, ніж бітрейт: 127,7 кбіт/с замість 128. Програвачі, що рахують тривалість
  із розміру й бітрейту (так робить і стандартний програвач Windows), показували б годину як 59:52. Тому
  `pad_frames` ставить у копії типу `MPEGLAYER3_FLAG_PADDING_ISO`: кодер її приймає, і бітрейт виходить
  точним. На 48, 16 і 8 кГц доповнення не потрібне.
- **Перевірка MP3** читає файл кадр за кадром: у кожному кадрі та сама версія MPEG, частота, канали й
  бітрейт, файл закінчується рівно на кінці кадру. Файл MP3 завжди довший за запис: кодер затримує звук
  приблизно на 1201 семпл і дописує кадри до кінця. Заміряно (Windows 11): довший на 1729–2880 семплів у
  MPEG-1 і на 1729–2304 у MPEG-2 та 2.5, тобто на 36–60 мс на 48 кГц, 108–144 мс на 16 кГц, 216–288 мс на
  8 кГц. Перевірка вимагає, щоб файл був довший за запис щонайменше на 1152 семпли (вміщав увесь запис і
  затримку кодера) і щонайбільше на 4032 (`MIN_EXTRA`, `MAX_EXTRA`). Порожній запис дає файл із двома
  кадрами тиші, який програвач відкриває.
- **Media Foundation** (`convert/media_foundation.rs`). У Windows N і KN без Media Feature Pack немає ні
  кодера, ні `mfplat.dll`. Програма, що імпортує `mfplat.dll` звичайним способом (так роблять функції `MF*`
  крейта `windows`), там навіть не запускається. Тому `mfplat.dll` завантажується з System32 під час першої
  конвертації в MP3 (`LoadLibraryExW`), а п'ять потрібних функцій викликаються через вказівники; інтерфейси
  (`IMFTransform` тощо) і GUID беруться з крейта і імпорту не потребують. Не викликайте функцій `MF*` крейта
  напряму: перевірити можна командою `dumpbin /dependents` на зібраному exe, у списку не має бути
  `mfplat.dll`, `mf.dll` чи `mfreadwrite.dll`. Якщо бібліотеки або кодера немає, конвертація закінчується
  помилкою `ConvertError::NoEncoder`: WAV лишається, а вікно каже, як установити Media Feature Pack.
- **Перемикач для перевірок.** Змінна середовища `AUDIOCAPTOR_NO_MP3_ENCODER=1` змушує програму поводитися
  так, ніби кодера MP3 немає (`mp3::NO_ENCODER_SWITCH`). Нею `just smoke` перевіряє повідомлення для
  Windows N; іншого впливу вона не має.
- **FLAC** (`convert/flac.rs`): libFLAC 1.5.0 через крейт `libflac-sys`, кодер і декодер викликаються
  напряму (рішення decision-10). Рівень стиснення 5, блок 4096 кадрів, таблиця переходів із точкою кожні
  10 с, MD5 звуку в блоці STREAMINFO. Частота й канали лишаються як у записі: 8, 16, 44,1 і 48 кГц, моно й
  стерео; нічого не перетворюється й не зводиться. Кодер пише файл через власні функції write, seek і tell
  (`FLAC__stream_encoder_init_stream`): наприкінці libFLAC сама повертається на початок файлу й дописує
  довжину, MD5 і таблицю переходів. WAV читається блоками по 4096 кадрів, тож пам'ять не росте з тривалістю
  запису. Порожній запис дає правильний файл без звуку. `encode_share` — 0,7.
- **Перевірка FLAC** — звірка з WAV семпл у семпл (рішення decision-7). Декодер libFLAC розкодовує весь
  файл з увімкненою перевіркою MD5, кожен блок порівнюється з тими самими кадрами WAV, а наприкінці і
  кількість звірених кадрів, і довжина в STREAMINFO мають дорівнювати кількості кадрів запису. Помилка — це
  також будь-яке повідомлення декодера (втрачена синхронізація, хибна контрольна сума блока), MD5 із самих
  нулів і блок з іншою частотою чи кількістю каналів, ніж у STREAMINFO. Кодер і перевірка дивляться на
  прапорець зупинки на кожному блоці. У збиранні без `NDEBUG` (тести, `just dev`) libFLAC, натрапивши на
  пошкоджений файл, пише в stderr рядки на кшталт «Rewinding, seeking necessary»: у тестах пошкоджених
  файлів це очікувано.
- **Заміри FLAC** (TASK-12, зібраний exe, ПК розробки з i5-14500): година 48 кГц стерео конвертується за
  13,5 с — і мовлення (файл 126 МБ, 18 % від WAV), і музика (384 МБ, 56 %); запис на 6 год 30 хв (WAV
  4,49 ГБ з переповненим заголовком) — за 69 с. Приватна пам'ять процесу під час конвертації — 8,0 МБ, без
  неї — 7,7 МБ. Exe більший на 137 КБ, нових DLL серед залежностей немає.
- **Черга** (`convert/queue.rs`): один потік `converter` бере файли по одному, в порядку зупинки. Файл, який
  конвертується, лишається першим у черзі й у `conversion-queue.json`, доки не готовий. Файл, який не вдалося
  конвертувати, з черги зникає: повторних спроб немає, користувачеві лишається WAV. Запис із форматом, якого
  версія не знає, і запис, чий WAV зник, під час читання файлу черги пропускаються. Потік працює у фоновому
  режимі Windows (`THREAD_MODE_BACKGROUND_BEGIN`: нижчий пріоритет процесора й диска), тож запис, що йде
  водночас, має перевагу й на слабкому комп'ютері; на вільному комп'ютері конвертація однаково бере ціле ядро.
- **Старт.** Чергу читає `setup`, але потік запускає вікно командою `start_conversions`, коли вже слухає
  події черги: інакше воно могло б пропустити кінець короткої конвертації. Перед цим вікно питає
  `conversions_left_over`, скільки записів лишилося з минулого запуску, і оголошує це.
- **Вихід.** Будь-який вихід із програми доходить до `RunEvent::Exit` у `run()`: там `ConversionQueue::shutdown`
  зупиняє потік і чекає на нього. Кодер перевіряє прапорець зупинки на кожному кадрі, тож це мілісекунди;
  тимчасовий файл видаляється, WAV і файл черги лишаються, і наступний запуск починає цей файл заново.
- **Події для вікна:** `conversion-status` (скільки файлів лишилося, скільки чекає, формат, частка готового,
  оцінка часу для всієї черги; під час конвертації — двічі на секунду) і `conversion-failed` (шлях до WAV, що
  лишився, формат і `noEncoder`: чи бракує Windows кодера, тоді повідомлення каже про Media Feature Pack). Подія `recording-state-changed` зі станом `Idle` і відповідь команди `stop_recording` несуть
  `conversion`: скільки файлів запису стало в чергу й скільки вже чекало. З цього вікно складає одне оголошення
  про зупинку («Запис зупинено. Конвертацію в Opus розпочато»).
- **Порядок подій після зупинки.** `stop_and_convert` надсилає `recording-state-changed` зі станом `Idle`
  одразу після того, як поставив файли в чергу, тож вікно отримує зупинку раніше за події потоку
  `converter` про цей запис. Зупинка з вікна (синхронна команда `stop_recording`) і з меню трея працює в
  головному потоці: його події йдуть у WebView2 одразу, а події інших потоків чекають, доки він звільниться.
  Довгий натиск глобальної клавіші зупиняє запис зі свого потоку, і там зупинка випереджає звіт конвертації
  лише тому, що потоку `converter` для звіту треба більше часу. Затримка звітів після зупинки (розділ
  «Доступність») покладається на цей порядок, тож не робіть `stop_recording` асинхронною і не надсилайте
  стан після того, як розбудили потік `converter`.
- **Звук попередження** про невдалу конвертацію не грає, поки триває інший запис: програма не пускає власні
  звуки в записи. Повідомлення у вікні з'являється завжди.
- **Невдала конвертація й NVDA.** Повідомлення з шляхом до WAV показує блок помилки (`role="alert"`), і NVDA
  читає його одразу. Але якщо `alert` з'являється серед змін фокуса (збій у першу мить після запуску
  програми), NVDA його пропускає. Тому завершальне оголошення черги в області `role="status"`, яке NVDA
  читає завжди, саме каже, скільки записів лишилося у WAV («Conversion finished with errors. Recordings
  kept as WAV: 1.»).

Щоб додати формат: варіант у `OutputFormat` (ідентифікатор і назва для повідомлень), свій `Codec` і рядок у
`convert::codec_for`, пункт списку `outputFormats` у `ProfileDialog.svelte` з текстами в `messages/`, тип
`OutputFormat` у `src/lib/types/index.ts`, опис у README.

Тести MP3 (`convert/mp3.rs`) кодують справжнім кодером Windows і розкодовують його ж декодером MP3. На
GitHub `windows-latest` компонента Media Foundation немає (Windows Server без Server-Media-Foundation), тож
там, де задано змінну `CI`, ці тести пропускаються й пишуть «Skipped: this Windows has no MP3 encoder».
Деінде відсутній кодер — помилка тесту. Перевірка кадрів, межі тривалості й відсутній кодер тестуються й
без Media Foundation.

Тести FLAC (`convert/flac.rs`) кодують і розкодовують самою libFLAC, від Windows не залежать і йдуть також
на CI.

### Команди IPC

Інтерфейс звертається до бекенду через команди IPC Tauri. Основні з них:

| Команда | Напрям |
|---------|--------|
| `get_audio_devices` | Інтерфейс → бекенд |
| `start_recording` | Інтерфейс → бекенд |
| `pause_recording` | Інтерфейс → бекенд |
| `resume_recording` | Інтерфейс → бекенд |
| `stop_recording` | Інтерфейс → бекенд |
| `load_settings` / `save_settings` | Інтерфейс ↔ бекенд |
| `conversions_left_over` / `start_conversions` | Інтерфейс → бекенд |
| `recording-state-changed` | Бекенд → інтерфейс (подія) |
| `conversion-status` / `conversion-failed` | Бекенд → інтерфейс (події) |

Повний список команд — у `tauri::generate_handler!` у `src-tauri/src/lib.rs`; події бекенд надсилає
викликами `emit`.

### Глобальна гаряча клавіша

Глобальна гаряча клавіша (типово `Pause/Break`) розрізняє короткий і довгий натиск:

| Поточний стан | Короткий натиск (<500 мс) | Довгий натиск (≥500 мс) |
|---------------|---------------------------|-------------------------|
| Очікування | → Почати запис | → Почати запис |
| Запис | → Пауза | → Зупинити |
| Пауза | → Продовжити | → Зупинити |

Довгий натиск зупиняє запис, щойно клавішу протримали 500 мс, не чекаючи, поки її відпустять.

Якщо активний профіль записує з пристрою, який не вибрано, натиск в очікуванні не починає запису, а
відтворює звук попередження й пише про це рядок у журнал (`device_missing` у `src-tauri/src/hotkey.rs`).

## Доступність

Доступність — **найважливіша вимога**:

- Усі елементи інтерфейсу мають ARIA-підписи й ролі.
- Повне керування з клавіатури (Tab, Enter, Escape).
- Комбінації з Alt: Alt+S (старт), Alt+P (пауза), Alt+R (продовження), Alt+T (стоп), Alt+I (поточний стан).
  Коли профіль потребує пристрою, який не вибрано, Alt+S не починає запису, а оголошує ту саму підказку, що
  й назва вимкненої кнопки Start («Select a system audio device»); фокус лишається на місці. Текст
  підказки має одне джерело: `readinessHint` у `src/lib/stores/recording.svelte.ts` (TASK-38).
- Область `aria-live` оголошує зміни стану екранним читачам. NVDA читає її лише тоді, коли текст змінюється,
  тож усі оголошення йдуть через `announce()` в `src/App.svelte`: той самий текст двічі поспіль (Alt+I
  у тому самому стані) отримує в кінці невидимий пробіл нульової ширини (U+200B), і NVDA читає його знову.
- Конвертація в стиснений формат теж оголошується: її початок (разом із зупинкою запису, одним
  оголошенням), завершення всієї черги і продовження після запуску. Alt+I під час конвертації додає, що
  вона триває, скільки приблизно лишилося для всієї черги і скільки файлів чекає. Рядок із відсотком під
  таймером бачать зрячі користувачі; оголошень він не робить.
- Після зупинки запису NVDA спершу каже про зупинку, а потім — чим закінчилася конвертація, навіть коли
  вона закінчилася одразу (TASK-39). Тому завершення черги й повідомлення про невдалу конвертацію в блоці
  помилки чекають, доки від оголошення зупинки мине 3 с (`STOP_READ_MS` і `reportConversion()` в
  `src/App.svelte`), і йдуть у тому порядку, в якому прийшли; пізніші звіти не чекають. Без цього
  конвертація, що закінчилася одразу, замінювала оголошення зупинки: зміни, що сталися майже водночас,
  доходять до NVDA разом, і він читає лише останній текст. А блок помилки (`role="alert"`) NVDA читає з
  найвищим пріоритетом (`Spri.NOW`) і перебиває ним те, що каже.
- Фокус не лишається на вимкненому чи прибраному елементі й не падає на сторінку. Після закриття діалогу
  він повертається туди, звідки діалог відкрили (після збереження чи видалення профілю — на список
  профілів). Коли зміна стану запису вимикає чи прибирає елемент із фокусом, фокус переходить на першу
  кнопку запису нового стану (Start, Pause чи Resume). Фокус переносять один раз і одразу на кінцевий
  елемент (doc-3).
- Діалог налаштувань оголошує свої дії через власну ділянку `role="status"` усередині діалогу (TASK-47), а не
  через `announce()` головного вікна: та ділянка лежить поза модальним діалогом (`aria-modal="true"`), і NVDA
  може її пропускати. Його `announce()` має той самий прийом із U+200B. Оголошує він таке: після «Захопити» —
  «Натисніть клавішу. Escape — скасувати»; Escape під час захоплення — «Захоплення клавіші скасовано» (фокус
  спершу йде на поле клавіші, бо зміна фокуса обриває мовлення NVDA, а потім звучить оголошення); клавіша, якої
  не вдалося задати (TASK-49), — «Не вдалося задати … гарячою клавішею: …», з її назвою, причиною і старою
  клавішею (чи що клавіші й далі немає); захоплення тоді закінчується, стара клавіша реєструється знову,
  `updateHotkey` нічого не записує в стан (він міняє стан лише після успішної реєстрації), а фокус лишається
  на «Захопити», тож можна одразу пробувати іншу. Відмова буває двох видів: розбір клавіші в
  `hotkey::parse` не знає її коду (кирилична буква за української розкладки, як `Ctrl+Й`, символ зі Shift,
  як `Ctrl+Shift+!`, клавіша меню `ContextMenu`) — тоді поточна клавіша лишається зареєстрованою; або
  `RegisterHotKey` відмовляє, бо клавішу тримає інша програма. Другий випадок майже не трапляється під час
  захоплення: таку клавішу Windows віддає тій програмі, і вікно її не бачить. Текст причини правдивий для обох;
  «Очистити» —
  «Гарячу клавішу очищено»; зміна мови — підказку про перезапуск, лише коли нова мова відрізняється від мови,
  з якою програму запущено (`getLocale()`). Закритий `<select>` у WebView2 міняє значення й шле `change` на
  кожну стрілку, тож без цієї умови повернення до своєї мови теж казало б підказку. Кнопка «Захопити» під час
  захоплення не вимикається (на ній фокус) і не міняє `aria-label`: NVDA читає нову назву елемента з фокусом, і
  разом з оголошенням це звучало б двічі; видимий текст міняється. Підказки під списком «Мова» й групою «Тема»
  прив'язано через `aria-describedby` (у групи — до самої групи, тож NVDA читає її раз за вхід у групу). Поле
  клавіші називається «Глобальна гаряча клавіша: Pause» чи «…: не задана».
- Діалоги відкриваються один поверх одного («About» за F1 чи з меню трея — поверх будь-якого). Зверху
  малюється той, що відкрито останнім, тобто той, де фокус: фон кожного діалогу (`.dialog-backdrop`) має
  `{@attach bringToFront}` з `src/lib/utils/dialogLayer.ts`, а не сталий `z-index`.
- `decorations: true` у конфігурації Tauri (потрібно для сумісності з екранними читачами).
- Клавіші й меню браузера вимкнено (TASK-44, `src-tauri/src/webview.rs`): F5 і Ctrl+R перезавантажували
  сторінку, і вікно скидалося, а Ctrl+P, Ctrl+F, F3, Ctrl+G, Shift+F10 і правий клік відкривали друк, пошук
  чи меню браузера. Tauri 2.12 таких налаштувань не має, тож `setup` через `with_webview` ставить у WebView2
  `AreBrowserAcceleratorKeysEnabled` і `AreDefaultContextMenusEnabled` у `false`. WebView2 може застосувати їх
  лише з наступної навігації, а сторінка тоді вже вантажиться, тому два обробники діють одразу:
  `AcceleratorKeyPressed` поглинає перелічені клавіші, а `ContextMenuRequested` — меню. Клавіші редагування
  (Ctrl+C, Ctrl+V, Ctrl+X, Ctrl+A, Ctrl+Z) не належать до клавіш браузера й працюють.
- Svelte під час компіляції перевіряє доступність; попередження показує `pnpm check`.
- Звукові сигнали дублюють зміни стану на екрані.
- `<body role="application">` в `index.html` не пускає NVDA в режим огляду, тож клавіші доходять до програми.
  Через це кожен текст, який користувач має почути, мусить бути підписом, описом або оголошенням. Чому так і
  як режими огляду й фокуса NVDA працюють у WebView2 — документ doc-3 у Backlog
  (`backlog doc view doc-3 --plain`).
- Назву «AudioCaptor» має лише заголовок вікна (`tauri.conf.json`). `<title>` в `index.html` порожній,
  `<body role="application">` не має `aria-label`, а інтерфейс у `App.svelte` лежить у звичайному блоці, не в
  орієнтирі `main`. Коли вікно вперше отримує фокус, NVDA, перш ніж назвати елемент із фокусом, називає вікно,
  документ сторінки (двічі: сам документ і його копію для режиму огляду) і `application`. Будь-яка назва на цих
  рівнях повторювала б назву вікна (TASK-18), тож не додавайте їх і не обгортайте інтерфейс у нові орієнтири.
- Зміни в інтерфейсі, фокусі, діалогах чи оголошеннях перевіряють з клавіатури і з NVDA, зокрема тестом
  `just smoke` (наступний розділ).

## Перевірка з NVDA (`just smoke`)

`just smoke` перевіряє зібраний exe разом з NVDA: скрипт `scripts/smoke-nvda.ps1` натискає клавіші
замість користувача й читає з журналу NVDA, що той сказав на кожному кроці. Перевірка лише локальна:
CI і Release її не запускають.

Що потрібно:

- Зібраний exe: `just build`. Тест бере `src-tauri/target/release/AudioCaptor.exe`; інший exe —
  параметр `-Exe`. Якщо код змінено після збірки, звіт про це попереджає.
- Запущений NVDA з рівнем журналу «Введення/виведення» (меню NVDA → Параметри → Налаштування →
  Загальні → Рівень журналювання). Тест шукає `nvda.log` у теці `%TEMP%`; інший шлях — параметр
  `-NvdaLog`. Якщо NVDA не запущено або він не пише мовлення в журнал, тест зупиняється з
  поясненням і кодом виходу 2.
- Пристрій відтворення за замовчуванням у Windows: сценарій `record` записує системний звук.
- Руки геть від клавіатури й миші від старту до трьох сигналів наприкінці: тест забирає
  клавіатуру, мишу й голос NVDA на дві-три хвилини (усі сценарії — близько трьох хвилин, з
  них сценарій `convert` — близько 50 с, `mp3` — близько 20 с, `flac` — близько 20 с).
- Для сценарію `convert` — близько 900 МБ вільного місця в теці `%TEMP%`: тест генерує там WAV,
  який програма конвертує, і видаляє його наприкінці сценарію.

Запуск:

- `just smoke` — усі сценарії, `just smoke <сценарій>` — один (кілька — через пробіл). Кожен
  сценарій запускає програму заново й наприкінці закриває її:
  - `launch` — NVDA називає вікно («AudioCaptor») один раз, а потім список профілів, і не читає вікно
    через UI Automation («веб-вміст», адреса сторінки); Tab обходить усі елементи керування, у кожного
    є назва, і NVDA її читає;
  - `record` — Alt+S, Alt+P, Alt+R і Alt+T оголошують новий стан рівно один раз (Alt+R — «Recording resumed», а не
    «Recording started»), Alt+I — поточний, а друге Alt+I поспіль знову каже «Ready» (TASK-35). Коли елемент із фокусом вимикається чи зникає (Alt+S на
    списку профілів, Alt+P на Pause, Alt+R на Resume, Alt+T на Stop), фокус переходить на кнопку
    нового стану, і NVDA називає її, не кажучи «недоступно» і не називаючи сторінку («AudioCaptor»,
    «документ», «додаток»); фокус на Stop під час паузи лишається на місці. Запис справді
    починається (системний звук, мікрофон не потрібен), але файл WAV тест не перевіряє. Під час запису
    клавіші браузера (F5, Shift+F5, Ctrl+R, Ctrl+Shift+R, Ctrl+P, Ctrl+F, F3, Ctrl+G) і клавіші меню
    (Shift+F10, клавіша контекстного меню) нічого не роблять: сторінка не перезавантажується, а друк,
    пошук чи меню не забирають фокус з Pause (TASK-44);
  - `nodevice` — у налаштуваннях не вибрано пристрою системного звуку, а активний профіль записує
    системний звук: Alt+S на списку профілів не починає запису, NVDA каже «Select a system audio
    device» (ту саму підказку, що в назві вимкненої кнопки Start), фокус лишається на списку, а
    друге Alt+S каже це знову (TASK-38). Звук попередження глобальної клавіші тест почути не може:
    умову, за якої він звучить, перевіряють модульні тести `device_missing` у `src-tauri/src/hotkey.rs`;
  - `dialogs` — «About AudioCaptor» (F1), налаштування, новий профіль і підтвердження видалення:
    фокус заходить у діалог, Escape закриває його, і фокус повертається туди, звідки діалог
    відкрили. F1 у налаштуваннях відкриває «About» поверх них: посередині вікна UI Automation
    знаходить «About», а після Escape — знову налаштування. Назву кожного діалогу NVDA читає рівно один раз
    (перевірка `-Once`); у «About» фокус стоїть на кнопці Close, а не на заголовку (TASK-19). У
    налаштуваннях (TASK-47) поле клавіші звучить як «Global Hotkey: Pause»; після «Захопити» NVDA один раз
    каже «Press a key. Escape to cancel», а фокус лишається на ввімкненій кнопці; Escape скасовує
    захоплення з оголошенням, фокус іде на поле, клавіша в `settings.json` лишається Pause. Далі тест знову
    натискає «Захопити» і Ctrl+Shift+1: за англійської й української розкладки воно приходить як
    `Ctrl+Shift+!`, а розбір клавіш не має коду для «!» (TASK-49). NVDA один раз називає клавішу й причину, фокус
    лишається на кнопці, у журналі тестової копії з'являється ще один рядок «Global hotkey registered: Pause»
    (стара клавіша знову діє), `settings.json` лишає Pause, а Shift+Tab знову переходить на поле, що звучить
    як «Global Hotkey: Pause». Клавіша, яку заздалегідь займає сам тест, тут не годиться: Windows віддає її
    тій програмі, і до захоплення вона не доходить; тож тест не реєструє жодної гарячої клавіші. Вхід у групу
    «Тема» читає її підказку один раз, перехід усередині групи — ні; список «Language» читає підказку
    про перезапуск як опис, стрілка вниз — ще раз, стрілка вгору (назад до English) — ні. «Очистити»
    оголошує «Hotkey cleared», фокус лишається на кнопці, а поле читається як «Global Hotkey: not set».
    У діалозі нового профілю Tab доходить до списку «Format», NVDA читає його назву й значення, а стрілка вниз
    міняє формат. У діалозі редагування профілю тест вибирає «Opus — speech (mono)» і натискає Save:
    фокус повертається на список профілів, а профіль у `settings.json` має формат `OpusSpeech`.
    Наостанок тест вводить у полі Name нового профілю назву `zed` і зберігає її клавішею Enter;
    у наступному діалозі нового профілю NVDA не каже «містить автоматичне заповнення», і перший
    Escape закриває діалог (TASK-23: підказки автозаповнення WebView2 забирали собі перший Escape).
    Дані WebView2 тестової копії лишаються до кінця запуску, тож другий діалог бачить те, що лишив перший;
  - `tray` — Escape ховає вікно, повторний запуск exe показує його, і NVDA його оголошує;
  - `settings` — запуск із пошкодженим `settings.json`: програма лишає копію `settings.unreadable.json`, а NVDA
    читає повідомлення, що налаштування скинуто, і де лежить старий файл;
  - `convert` — конвертація в Opus (TASK-28). Тест кладе в теку записів два згенеровані WAV (великий і
    малий) і файл черги, ніби попередній запуск не встиг їх конвертувати. Після старту NVDA каже, що
    програма завершує конвертацію двох записів; Alt+I каже, що конвертація триває, скільки приблизно
    лишилося і що один файл чекає, а друге Alt+I за мить каже це знову; Alt+F4 відкриває попередження про вихід (фокус на Cancel, Escape його
    закриває); Alt+F4, Tab, пробіл на Exit закривають програму: обидва WAV цілі, файлів `.opus` і
    `.opus.tmp` немає, файл черги зберіг обидва записи. Другий запуск знову оголошує завершення
    конвертації; під час неї Alt+S починає запис, Alt+T зупиняє його («The recording is waiting to be
    converted to Opus»), Alt+I каже вже про два файли в черзі. Коли черга спорожніє, NVDA каже «Conversion
    finished», у теці лежать три файли `.opus` (серед них справжній запис системного звуку), а WAV і
    файлу черги немає; Alt+F4 тоді закриває програму без запитань. Наостанок третій запуск із записом,
    який не можна конвертувати (його WAV удвічі коротший, ніж каже черга): за кілька секунд NVDA читає
    повідомлення «Could not finish the conversion to Opus. The recording is kept as WAV: …», а потім
    «Conversion finished with errors. Recordings kept as WAV: 1.»; WAV лишається, файлів `.opus` і
    `.opus.tmp` немає. Великий WAV (параметр `-ConvertMB`,
    типово 900 МБ) має конвертуватися довше, ніж тривають кроки під час конвертації (близько 10 с): на
    ПК розробки це близько 30 с. Якщо на швидшому комп'ютері звіт каже, що конвертація
    закінчилася зарано, збільште число: `just smoke convert -ConvertMB 1800`;
  - `mp3` — конвертація в MP3 (TASK-29), близько 30 с. Активний профіль має формат «MP3 — стандарт»:
    Alt+S, три секунди запису системного звуку, Alt+T. NVDA каже «Recording stopped. Conversion to MP3
    started.», а потім «Conversion finished.», і в теці записів лежить один файл `.mp3`, який починається
    кадром MP3, і немає WAV. Потім програма запускається зі змінною `AUDIOCAPTOR_NO_MP3_ENCODER=1`, ніби
    у Windows немає кодера MP3 (Windows N без Media Feature Pack): після Alt+S і Alt+T конвертація
    закінчується невдачею одразу, але NVDA спершу каже «Recording stopped. Conversion to MP3 started.», а
    вже потім читає «Windows has no MP3 encoder. To record in MP3, install the Media Feature Pack…» і
    «Conversion finished with errors. Recordings kept as WAV: 1.» (TASK-39); запис лишається у WAV без
    файлів `.mp3` і `.mp3.tmp`. Порядок перевіряє параметр кроку `-First`: його текст має прозвучати
    раніше за тексти з `-Expect` і `-Once`;
  - `flac` — формат FLAC (TASK-12), близько 20 с. Активний профіль має формат «FLAC (lossless)». У
    діалозі редагування профілю Tab доходить до списку «Format», і NVDA читає його назву й значення
    «FLAC (lossless)»; Escape закриває діалог. Потім Alt+S, три секунди запису системного звуку, Alt+T:
    NVDA каже «Recording stopped. Conversion to FLAC started.», а потім «Conversion finished.», і в теці
    записів лежить один файл `.flac`, який починається позначкою `fLaC`, і немає WAV.
- Старт. Спершу тест перевіряє exe, NVDA і його журнал (якщо чогось бракує, він зупиняється
  одразу). Потім лунає один звуковий сигнал, і за 5 секунд тест натискає першу клавішу. Іншу паузу
  задає параметр `-PauseSec`, наприклад `just smoke dialogs -PauseSec 10`.
- Дозвіл. Агент перед кожним запуском `just smoke` питає власника в чаті (запустити, відкласти
  тощо) і запускає тест лише після «так». Сам скрипт нічого не питає.
- Кінець. Коли звіт готовий, лунають три сигнали, якщо сценарії відпрацювали (код 0 чи 1), або два
  нижчі, якщо тест зупинився (код 2: чогось бракує, невідомий сценарій чи
  параметр). Сигнали — це звук, який скрипт грає через пристрій відтворення за замовчуванням, тож
  їх чути там, де й решту звуків Windows.
- Звіт (англійською) друкується в консоль і зберігається в `%TEMP%\audiocaptor-smoke-report.txt`:
  для кожного кроку — результат, що сказав NVDA і які перевірки не пройшли, а наприкінці — список
  невдалих кроків. Код виходу: 0 — усе пройшло, 1 — є невдалі кроки або тестова копія писала в
  `%LOCALAPPDATA%\com.audiocaptor.app`, 2 — тест не запустився або зупинився (причину названо у звіті).
- Тестова копія працює з англійським інтерфейсом. Слова ролей, які NVDA каже своєю мовою
  (наприклад, «діалог»), тест приймає англійською й українською.

Що тест не чіпає:

- Тест запускає копію exe з `%TEMP%\audiocaptor-smoke` з власною `AudioCaptor-data` (англійський
  інтерфейс, два тестові профілі, вибрано пристрій відтворення за замовчуванням). Профілі в тестовому
  `settings.json` записано як у версії 5, без формату, тож кожен запуск тестової копії проходить і
  міграцію налаштувань до версії 6; лише сценарії `convert`, `mp3` і `flac` дають активному профілю
  формат («Opus — мовлення», «MP3 — стандарт», «FLAC»). Дані WebView2 ця
  копія, як і будь-яка інша, тримає в `AudioCaptor-webview` поруч зі своїм exe: тест перевіряє, що вона
  сама створила там `EBWebView`, а звіт показує стан цієї теки. Кожен прогін починається з порожнім
  профілем браузера, як перший запуск нової копії чи запуск після оновлення через Scoop.
- Версії до 0.1.1 включно тримали дані WebView2 в `%LOCALAPPDATA%\com.audiocaptor.app\EBWebView`. Під
  час тесту в `%LOCALAPPDATA%\com.audiocaptor.app` нічого не має змінитися, а якщо цієї теки не було,
  вона не має з'явитися: усі свої дані програма тримає поруч з exe (рішення decision-1). Звіт
  показує, що `EBWebView` там не змінилася, а будь-яка зміна в цій теці — і в `EBWebView`, і деінде,
  наприклад у `logs` — означає, що тест не пройшов. У цій теці тест читає лише назви верхніх
  елементів, кількість файлів і тек у кожному та час найновішої зміни.
- Наприкінці тека тесту видаляється, а журнал тестової копії лишається в
  `%TEMP%\audiocaptor-smoke-app.log`.
- Якщо працює ваш AudioCaptor, тест просить його закритися, як це робить кнопка закриття вікна,
  і потім не запускає його знову; звіт про це каже. Програма дозволяє лише одну копію й тримає
  клавішу Pause/Break. Якщо ваш AudioCaptor не закрився (наприклад, іде запис і він питає, чи
  зупинити), тест зупиняється й програму не чіпає. Тож не запускайте тест під час запису.
- Поки тестову копію сховано чи закрито, фокус стоїть у маленькому вікні скрипта («Smoke test
  home»), тож NVDA не читає у звіт ваших інших програм. Сповіщення, які NVDA прочитає під час
  прогону, у звіт таки потраплять: щоб їх не було, увімкніть режим «Не турбувати».
- З журналу NVDA тест читає лише те, що записано під час прогону.

Запускайте після змін в інтерфейсі, фокусі, діалогах, оголошеннях, показі чи хованні вікна, а
також після оновлення Tauri чи WebView2. Новий елемент головного вікна додавайте до `$TabOrder` у
скрипті, новий текст — до `$UI` (англійські рядки з `messages/en.json`).

Скрипт написано для Windows PowerShell 5.1 і лише символами ASCII: файл без BOM ця версія читає в
кодуванні ANSI. Українські слова записано в ньому як послідовності `\u`.

## CI

### Workflow на GitHub

| Workflow | Коли запускається | Що робить |
|----------|-------------------|-----------|
| **CI** (`ci.yml`) | pull request у `develop` або вручну (`workflow_dispatch`); push нічого не запускає | Ті самі перевірки, що `just check`, у тому самому порядку: Rust з `rust-toolchain.toml`, Node 22, pnpm з `packageManager` у `package.json` |
| **Release** (`release.yml`) | лише вручну (`workflow_dispatch`) | Звіряє версію й тег, бере опис релізу з `CHANGELOG.md`, виконує ті самі перевірки, що `just check`, збирає `AudioCaptor.exe`; публікує GitHub Release лише з вимкненим `dry_run` |

Перевірки й збирання йдуть на `windows-latest`; завдання `publish` у Release — на `ubuntu-latest`.

### Ручний запуск CI

```powershell
gh workflow run ci.yml --ref <гілка>
```

Те саме — кнопка «Run workflow» у вкладці Actions. Гілку спершу треба відправити на GitHub. Стан запусків
показує `gh run list --workflow ci.yml -L 3`.

Коли задача змінює CI, збирання чи залежності, перед її закриттям власник просить прогнати її гілку через CI
вручну. Червоний запуск стає задачею-помилкою.

## Випуск

### Що робить Release

Release робить усе по черзі й зупиняється на першій помилці, ще до тегу й релізу:

1. Звіряє введену версію з `package.json`, `src-tauri/Cargo.toml` і `src-tauri/tauri.conf.json`
   і перевіряє, що тегу `v<версія>` ще немає (див. «Захист від повторної версії» нижче).
2. Бере опис релізу — розділ `## [<версія>]` з `CHANGELOG.md`. Немає розділу — немає релізу.
3. Ставить Rust із `rust-toolchain.toml` і виконує ті самі перевірки, що `just check`.
4. Збирає `AudioCaptor.exe`, показує його хеш SHA256 у підсумку запуску й кладе exe разом з описом релізу в
   артефакти запуску (зберігаються 7 днів).
5. Лише коли `dry_run` вимкнено, окреме завдання `publish` створює тег `v<версія>` на зібраному коміті
   й реліз з файлом `AudioCaptor.exe`. Тільки воно має право запису в репозиторій.

Параметри запуску: `version` — версія без `v` (наприклад, `0.1.1`); `dry_run` — пробний запуск, увімкнений за
замовчуванням; `prerelease` — позначити реліз на GitHub як попередній. Попередній реліз однаково справжній:
правило «Чому не можна створювати справжній реліз для перевірки» діє й для нього.

### Порядок випуску

Приклад для версії 0.1.1; для іншої версії замініть номер. Push і запуск workflow — тільки з дозволу власника.

1. **Підготовка.** Задачі випуску закрито, їхні гілки завершено, `develop` чистий, `just check` проходить.
   У `CHANGELOG.md` розділ `## [Unreleased]` містить зміни, помітні користувачам.
2. **Гілка випуску** від `develop`:

   ```powershell
   git flow release start 0.1.1
   ```

   Команда створює гілку `release/0.1.1`.
3. **Версія в трьох файлах.** Нова версія вписується в:
   - `package.json` — поле `"version"`;
   - `src-tauri/Cargo.toml` — `version` у розділі `[package]`;
   - `src-tauri/tauri.conf.json` — поле `"version"`.

   Потім `just check`: cargo сам запише нову версію пакета `audio-captor` у `src-tauri/Cargo.lock`, а
   перевірки мають пройти. Release звіряє лише три файли, тож забутий `Cargo.lock` він не помітить:
   `git status` має показати всі чотири.
4. **CHANGELOG.** Заголовок `## [Unreleased]` стає `## [0.1.1] — <дата>` (дата у форматі `2026-04-20`, як у
   розділі 0.1.0), а над ним з'являється новий порожній `## [Unreleased]` для наступних змін. Унизу файлу
   додається посилання `[0.1.1]: https://github.com/ruslan-rv-ua/AudioCaptor/releases/tag/v0.1.1`. Розділ
   0.1.1 Release візьме описом релізу на GitHub, тож у ньому — лише зміни для користувачів, кожен пункт одним
   рядком.
5. **Коміт** цих п'яти файлів на гілці випуску.
6. **Пробний запуск на гілці випуску** (докладно — «Пробний запуск» нижче). Гілку відправляють на GitHub і
   запускають на ній пробний Release; він має бути зеленим:

   ```powershell
   git push origin release/0.1.1
   gh workflow run release.yml --ref release/0.1.1 -f version=0.1.1 -f dry_run=true
   ```

   Пробний запуск іде до злиття в `main`, щоб помилка (скажімо, одруківка у версії чи в `CHANGELOG.md`) не
   потрапила в `main`. Якщо запуск червоний, виправлення комітять на гілці випуску, знову відправляють її на
   GitHub і повторюють пробний запуск.
7. **Завершення:**

   ```powershell
   git flow release finish 0.1.1 --notag
   ```

   Команда зливає `release/0.1.1` у `main`, оновлює `develop` від `main` і видаляє гілку випуску. `--notag`
   означає, що git flow не створює тег: тег `v0.1.1` створить Release на GitHub. Тег, створений і
   відправлений вручну, зупинив би справжній запуск (див. «Захист від повторної версії»). Налаштування git
   flow живуть лише в `.git/config`, тож у новому клоні без `--notag` тег з'явився б знову.
8. **Відправити обидві гілки на GitHub і прибрати там гілку випуску:**

   ```powershell
   git push origin main develop
   git push origin --delete release/0.1.1
   ```

   Якщо гілки випуску на GitHub уже немає, друга команда лише скаже про це.
9. **Справжній запуск** на `main` — з того самого коду, що пройшов пробний запуск:

   ```powershell
   gh workflow run release.yml --ref main -f version=0.1.1 -f dry_run=false
   ```

10. **Перевірити реліз:**

    ```powershell
    gh release view v0.1.1
    ```

    Реліз має тег `v0.1.1`, файл `AudioCaptor.exe` і опис із розділу `CHANGELOG.md`. Завантажений exe
    запускається, а діалог «About» показує нову версію.
11. **Scoop.** Excavator у `ruslan-rv-ua/scoop-bucket` знаходить новий реліз упродовж доби, а одразу — якщо
    запустити його вручну (див. «Оновлення Scoop-маніфесту»). Після цього `bucket/audiocaptor.json` показує
    нову версію, і користувачі отримують її через `scoop update`.

### Пробний запуск

Пробний запуск (`dry_run`, увімкнено за замовчуванням) проходить усі кроки, крім публікації:
звірку версії, CHANGELOG, перевірки й збірку. Завдання `publish` пропускається, а збірка працює
з токеном лише для читання, тож тегу й релізу не буде навіть через помилку в workflow.
Зібраний exe можна завантажити з артефактів запуску й перевірити вручну.

Запуск на будь-якій гілці, відправленій на GitHub (версія має збігатися з версією в коді цієї гілки):

```powershell
gh workflow run release.yml --ref <гілка> -f version=<версія> -f dry_run=true
```

Те саме — кнопка «Run workflow» у вкладці Actions: вибрати гілку й лишити позначку `dry_run`. Стан запусків
показує `gh run list --workflow release.yml -L 3`.

**Чому не можна створювати справжній реліз для перевірки.** Кожен опублікований реліз упродовж доби
забирає Excavator у `scoop-bucket` і роздає користувачам Scoop як нову версію. Видалити реліз
потім уже пізно: користувачі встигнуть його поставити, а маніфест посилатиметься на зниклий файл.
Тому зміни в `release.yml` перевіряють лише пробним запуском, а тег `v*` створюють тільки для
справжніх версій.

**Захист від повторної версії.** Одразу після звірки версії Release перевіряє, чи є на GitHub
тег `v<версія>`. Справжній запуск з такою версією зупиняється до збірки. Без цього
`softprops/action-gh-release` оновив би наявний реліз і замінив би в ньому `AudioCaptor.exe` новою
збіркою: хеш файлу змінився б, і маніфест Scoop із записаним старим хешем перестав би встановлюватись.
Пробний запуск з такою версією лише попереджає і йде далі — він нічого не публікує, тож його можна
робити з поточною версією коду, навіть якщо її реліз уже є.

### Оновлення Scoop-маніфесту

Цей репозиторій **нічого не надсилає** до `scoop-bucket`. Оновлення робить сам bucket:
його workflow **Excavator** читає поля `checkver` і `autoupdate` у `bucket/audiocaptor.json`,
знаходить новий реліз, збирає URL і бере хеш — і комітить оновлений маніфест.

Запускається він **вручну** з вкладки Actions репозиторію
[scoop-bucket](https://github.com/ruslan-rv-ua/scoop-bucket/actions), плюс раз на добу за розкладом як
підстраховка. У файлі розклад — 04:20 UTC, але GitHub запускає заплановані workflow із затримкою: у листопаді
2026 запуски за розкладом ішли близько 13:00 UTC. Натискати безпечно будь-коли: якщо оновлювати нема чого,
він нічого не змінює.

Раніше тут був workflow `update-scoop.yml`, який слав `repository_dispatch` до bucket
і для цього тримав секрет `SCOOP_BUCKET_TOKEN`. Обидва прибрано: PAT із правом запису
в чужий репозиторій треба ротувати, і він відмовляє мовчки — реліз проходить, а bucket
тихо лишається позаду.
